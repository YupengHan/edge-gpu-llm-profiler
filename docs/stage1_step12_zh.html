Stage 1 · Step 12 — Streaming TTFT / ITL 基准（含 prefix-cache 现场教学）

执行环境同 step 11。Server 容器 trtllm_serve_step11 持续运行 ~30 分钟，引擎 tp_1_pp_1（512/128 main, bf16）。日期：2026-05-11。

这一步要回答的问题

step 10 的 trtllm-bench latency 给了 TTFT/TPOT 的平均值和分位数，但是采不到"第 17 → 第 18 个 token 之间隔了多少 ms"这种 per-token 时序。Step 12 通过 OpenAI streaming SSE 协议解决这个问题——每个 token chunk 到达 client 的时刻都被精确记录下来，从而得到 ITL（Inter-Token Latency）的完整分布。

本步骤的目标：

  1. 用真实 HTTP 客户端打 step 11 起好的 server，跑 50 次（+5 warmup）请求
  2. 采到 TTFT 分布 和 逐 token ITL 分布
  3. 和 step 10 的 trtllm-bench 数字 cross-check，量化 HTTP/SSE 协议层的额外开销
  4. 顺便验证：在同一 prompt 重复的情况下，TRT-LLM 的 prefix cache 会不会作弊

故事线（这步实际经历了两轮）

第一轮跑炸了——不是脚本写错，而是 benchmark 方法论错了。整个过程是 Stage 1 里非常典型的"在 GPU 实测时学到比 runbook 多一倍东西"的样本，所以下面完整记录。

第一轮：单 prompt × 55 次 → 暴露两个陷阱

陷阱 0：prompt 太长 → 全员 400 BadRequest

最早我把 data/synthetic_512_128.jsonl（step 5 生成的 main 工作负载数据集）的第一行 input_ids decode 回文本，当 chat completions 的 user message。但这个数据是 token-norm-dist 出来的乱码（"qli ThemeData frameborder都没ograf nutsolverпрактик…"）。

关键观察：decode 出来的 token id 序列 不是 canonical 的 BPE 编码。tokenizer 再 encode 回去会变长——

步骤token 数解释
原始 input_ids512token-norm-dist 直接采样
decode→re-encode541非 canonical BPE，re-encode 走最长匹配，长度变了
+ chat template 包装570Qwen2.5 chat_template 额外 ~29 tokens（system + assistant marker）

Server 配置是 max_seq_len=640，要 prefill + max_tokens(128) ≤ 640。570 + 128 = 698 > 640，于是每条请求都被 server 拒掉：

ValueError: The sum of prompt length (570.0) and query length (0)
max_tokens (128) should not exceed max_seq_len (640)

修复：用 docker exec 在 server 容器里跑一段二分搜索，把 user content 截到 483 tokens，让 chat_template(user=text) 总长恰好 512，留 128 给 decode → 总 640 正好打满 max_seq_len。

学习要点： step 9 编引擎时 max_seq_len=640 = 512 input + 128 output。这是把整个上下文的容量算死的——任何 prefill 超出 (640 - max_tokens) 的请求都会 400。换句话说，引擎的 max_seq_len 是协议级的硬上限，不能在 server 端只调 max_tokens 绕过。
要想撑更长 prompt，必须重新跑 trtllm-bench build 把引擎重编（参考 step 17 的 1024/256）。

陷阱 1：单 prompt 重复 55 次 → prefix cache 作弊

截短后再跑，55 个请求全部成功。但是看 per-request 时序：

请求号TTFT (ms)注释
080.25cold start，第一次见这个 prompt
119.82↓ 立刻掉到 ~20 ms
221.42...
…15–22之后 54 次都在 15–22 ms 之间
5416.82最后一次仍然命中 cache

对比 step 10 的 TTFT 平均 51.77 ms，这里 TTFT 莫名其妙快了 3 倍。原因：

真凶 = prefix caching： step 9 编引擎时启用了 use_paged_context_fmha=True（log 里可见）。当后续请求的 prompt 前缀与之前请求重合时，TRT-LLM 会复用之前的 KV cache 页，prefill 阶段只算"新增的"那部分 token。 我们这里 55 个请求整个 prompt 都一样——server 第二次见就直接把第一次的 KV cache 整段拷过来，几乎不做 prefill，所以 TTFT 只剩"HTTP+SSE+第一个 token decode"的开销 ≈ 17 ms。

陷阱 2：合成 prompt 触发 refuse → 只输出 12 tokens

所有 55 个响应内容完全一样：

"I'm sorry, but I can't assist with that."

12 tokens，自然 EOS。Qwen2.5-Instruct 把那段乱码 token 当作"不可帮助的请求"拒绝了。后果：每条只能采到 11 个 ITL 间隔，远不够画 ITL 分布。

第一轮的处置

把这份"错误数据"留作教材保存：

  • results/stage1/benchmark_raw/streaming_512_128_singleprompt_cachebenchmark.jsonl
  • logs/stage1/streaming_512_128_singleprompt.log

它正好是 "prefix cache 命中时的 TTFT" 的现场数据，step 18 baseline summary 会引用。

第二轮：50 条各异 prompt → 干净的 baseline 数据

方法变化

三件事一起改：

  1. 每个请求一个独特 prompt。写了 scripts/generate_streaming_prompts.py，用 5 个指令模板 × 10 个 ML 系统主题 = 50 条，每条用二分搜索精确填到 chat-template 总长 = 512 tokens。这样：
    – 每条 prompt 都没被见过 → 每次 prefill 都是冷的 ↔ 对照 step 10 干净
    – 50 条 prompt 互相 prefix 不重合 → 测不出 cache
  2. 结尾加 "Write at least 220 words"。强迫模型生成长输出，max_tokens=128 才是真正生效的截断（finish_reason="length" 而非 stop），保证每条都能采到 127 个 ITL 间隔。
  3. 客户端支持 prompt 轮询。在 scripts/benchmark_streaming_openai.py 里加了 --prompts-file：读 jsonl，按 request_index % N 取 prompt。

命令

# 1. 生成 prompt 集（用 server 容器里的 tokenizer 算 token 数）
docker exec trtllm_serve_step11 python3 scripts/generate_streaming_prompts.py \
  --target-template-total 512 --num-prompts 50 \
  --out data/streaming_prompts_512.jsonl

# 2. 跑 streaming bench（host 上跑，连容器 server）
python3 scripts/benchmark_streaming_openai.py \
  --base-url http://localhost:8000/v1 \
  --model tp_1_pp_1 \
  --prompts-file data/streaming_prompts_512.jsonl \
  --max-tokens 128 --requests 50 --warmup 5 --temperature 0 \
  --workload-label 512_128 --backend-label trtllm-1.0.0-trt \
  --output results/stage1/benchmark_raw/streaming_512_128.jsonl

0 errors，全部 55 行 output_pieces=128，finish_reason="length"。TTFT 走势：

解读：

  • TTFT 从 54 → 16 ms（3.4× 提速）：prefill 几乎全省，剩下的全是 HTTP/SSE/uvicorn 开销 + 第一个 token 的 decode 时间
  • ITL 几乎不变（10.56 → 10.31）：cache 只省 prefill，decode 阶段每生成一个新 token 都必须走 28 层 transformer——所以 per-token 间隔不会变快
  • E2E 只省了 ~70 ms：TTFT 节省 ~38ms + 其他次要项；和 ITL × 127 的 ~1342ms 比，prefill 节省占比很小，说明这个工作负载是 decode-bound 不是 prefill-bound

与 step 10 的对照（这才是 step 12 真正的 baseline）

指标step 10 trtllm-bench latencystep 12 streaming COLD差值归因
TTFT mean51.77 ms54.28 ms+2.5 msHTTP request + SSE 第一个 chunk 编/解码 + Python uvicorn FastAPI 栈
TPOT / ITL mean9.85 ms10.56 ms+0.7 ms每个 SSE chunk 的 json.dumps + flush + recv 来回
E2E mean1302 ms1396 ms+94 ms0.7 × 127 + 2.5 + 第一个 chunk role marker 延迟
throughput / 用户98.30 tok/s92.20 piece/s-6%同上

公式校验：TTFT + ITL × (N-1) = 54.28 + 10.56 × 127 = 1395.4 ms，实测 1395.9 ms。误差 0.04%。两阶段 prefill+decode 模型在加了 HTTP 层后依然成立。

关键结论： trtllm-serve 的 HTTP/OpenAI 兼容层给单用户场景额外加上约 +5% TTFT、+7% ITL、+7% 总延迟。这是用流式 API 的"协议税"。如果你的产品做 streaming chat，这个税值得付（用户能看到 token 一个一个冒出来比延迟 100ms 然后一次到达体验更好）；如果做 batch offline 推理，没必要走 serve，直接 trtllm-bench / Python LLM API 更省。
