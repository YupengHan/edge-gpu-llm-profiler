Stage 1 · Step 14 — GPU 时序 + trtllm-serve /metrics 内观

日期 2026-05-11。Server 容器 trtllm_serve_step11。本步同时跑两条数据采集线：宿主端 1 Hz nvidia-smi CSV，server 端 /metrics drain。

本步的目的

到 step 13 为止我们已经能从客户端视角说："TTFT p95 = 58 ms, ITL p95 = 12 ms"。但客户端看不到三件事：

  1. GPU 在 decode 期间到底有多忙？是 SM 利用率 100%，还是常有 idle gap？
  2. 这台卡的功耗/温度/时钟在卡哪里？是 thermal-throttle，还是 TDP-bound，还是空闲？
  3. engine 内部每个 iter 实际花了多少 ms？我们 ITL 量的是客户端两个 SSE chunk 间隔，扣不掉 HTTP/uvicorn/Python 那一层是多少。

step 14 通过两条手段把这三件事打通：

视角工具采样率能看到的事
宿主端（OS 看 GPU）nvidia-smi -l 11 Hzmacroscopic util/power/temp/clock/mem trajectory
容器端（server 看自己）/metrics 端点每 iter 一条每个 prefill/decode iter 的精确延迟、KV cache 命中率、调度状态

故事线（这步实际跑了两遍）

第一遍 server 经过 step 12 + step 13 已经 Up 半小时，prefix cache 暖到不能再暖——所有 50 个 prompt 都在缓存里。结果 TTFT mean 17.74 ms（全是 cache hit）。同时发现 /metrics 是 "drain 语义"：第一次 curl 返回 13.8 MB，立刻清空；之后 curl 都是 []。第一次的 13.8 MB 因为没存盘丢了。

第二遍：docker restart trtllm_serve_step11 清掉 cache（GPU 内存里的 KV 池随 server 进程退出而释放），等 server 重新加载引擎（30 s），立刻 curl /metrics drain 掉任何 stale 数据，然后才跑 bench，最后再 curl 一次 /metrics 抓 6.5 MB 完整记录。

学习要点 — "drain 语义" vs "snapshot 语义"： Prometheus 风格的 metrics 端点通常是 snapshot（每次返回当前所有计数器的快照，counter 永远只增不减）。但 trtllm-serve /metrics 是 drain（返回上次拿走后新增的 iter 记录，并清空内部 buffer）。两种语义都常见——drain 适合"per-event 历史"，snapshot 适合"当前状态"。
判断方法：第二次连续 curl 看返回是缩小还是不变。缩小 → drain，不变 → snapshot。

注意： baseline util 是 20% 而不是 0%。原因：TRT-LLM 的 inflight batcher 即使没新请求也在持续 spin（iter loop 一直跑 numActiveRequests=0 的空 iter）。这是为了让新请求一到就能立刻调度，避免冷启动延迟，但意味着 server 24h 都在烧 ~35-40W。对你这台笔记本来说，这个 server 不能开着不用，电池会很难看。

关键观察 — decode 是 memory-bound： util.gpu = 97% 看似很饱和，但真正的瓶颈是 util.mem 82%——内存控制器在 80% 以上的时间都在搬 KV cache。每生成一个 token 都要把整个 sequence 的 KV pages 从 HBM 读出来过一遍 attention。这是 LLM decode 阶段的教科书式特征：算力（SM）富余，HBM 带宽不够用。
这意味着什么：换更猛的 SM（升级到 RTX 4090 Mobile，SM 算力翻倍）不会让 decode 翻倍快——HBM 带宽才是天花板。要想真加速，得用 INT8/INT4 量化（让 KV cache 变小，单 token 要读的字节数减半），或者用 FlashAttention v3 那种"避免重读"的算子。

其他要点：

  • 功率 114 W 卡在 RTX 3070 Laptop 的 cTGP 上限（115 W）——boost clock 上不去更多了
  • 温度 75 °C 远低于 throttle 阈值 87 °C，没有热降频
  • memory.used 全程 7437 MiB 不动——KV cache 池在 server 启动时就按 kv_cache_free_gpu_memory_fraction 全切完了，请求来不来都占着

trtllm-serve /metrics — 7095 条 iter 记录

每个 iter 一条 JSON，字段非常丰富。我们提取了三类核心信息：

(1) per-iter latency 与客户端 ITL 对齐

视角p50p90p95p99
客户端 flattened ITL (5715 gap)10.66 ms11.6312.0313.09
server generation iter latency (6985 iter)10.75 ms11.2911.5414.14
差值（HTTP/SSE 层税）+0.1 ms+0.3+0.5-1.0
这是 stage 1 第一次能分解 ITL： 服务端 engine inner loop 的 p50 是 10.75 ms（"模型计算 + 调度"），客户端最终看到的两个 chunk 间隔 p50 是 10.66 ms。
——等等，客户端比服务端还快 0.1 ms？这看似不可能。其实是因为客户端的 ITL 是 SSE chunk 到达间隔，而 server 端 iter 包含"上一个 token 解码 + 写入 detokenizer queue + 等待下一次调度"完整一圈。chunk 实际发送给客户端的瞬间是 iter 中点而不是末尾，所以客户端"两个 chunk 之间"刚好覆盖了 iter 末尾→下一个 iter 中点的距离，约等于一个 iter。所以 HTTP/SSE 单向延迟小于 0.5 ms，可以认为 trtllm-serve 这一层对 single-user 几乎无开销。

(2) context iter（prefill）的隐藏故事

统计值
context iters 总数55（恰好等于 5 warmup + 50 measured 请求数）
context iter latency p5010.87 ms
numCtxTokens 出现频次 top 5{465 ×9, 395 ×6, 433 ×6, 466 ×6, 459 ×6}

prefill 一次处理 465 tokens 只用 10.87 ms？看似不合理（512 tokens 全冷 prefill 按 step 12 cold TTFT 54 ms 估）。但 numCtxTokens 最高也只有 466 而不是 512——意味着每个请求其实只 prefill 了 465 个 token，剩下的 ~47 个已经在 cache 里了。

这 47 个就是 Qwen2.5 chat template 头：<|im_start|>system\n…helpful assistant.\n<|im_end|>\n<|im_start|>user\n。所有 50 个 prompt 共享这段前缀，request #0 之后就被 prefix cache 收编。所以 server 视角下的"cold"其实是"system prompt 之后的 cold"。

教训： 即使你认为这是 cold prefill，TRT-LLM 也会偷偷复用 chat template 头那 ~50 tokens 的 KV pages。客户端 TTFT 包含 HTTP 往返 + chat template 渲染 + tokenize + 队列 + 一次 prefill iter (~11 ms) + 第一个 chunk 序列化——加起来 ~55 ms。真正"完全冷"的 prefill 你永远不会在生产环境里看到，除非你每次重启 server。
