Stage 1 · Step 15 — Nsight Systems：把 1.4 秒 E2E 拆开看

日期 2026-05-11。本步在 1.0.0 容器里用 nsys profile 包了一次 trtllm-bench latency。tools available：nsys 2025.3.1, ncu 2025.2.1（容器自带）。

这一步要回答什么

到 step 14 为止我们已经知道：

  • 每生成一个 token (decode iter) 用 ~10.7 ms
  • GPU SM 利用率 97%、内存控制器利用率 82%
  • decode 是 memory-bound

但这些都是聚合数字。我们不知道：

  1. 这 10.7 ms 里，哪些 kernel 占了几毫秒？是 GEMM 占大头、还是 attention？
  2. GEMM 内部有几种 tile size？分别对应模型里哪一层？
  3. CPU 和 GPU 是串行的还是有重叠？
  4. 除了 kernel 之外，数据搬运（H2D/D2H/memset）占多少？

Nsight Systems 在 CUDA stream 时间线上把所有 kernel launch、memcpy、CUDA API、NVTX range、CPU 采样都连起来记。微秒级分辨率，足够分解一个 10 ms 的 iter。

命令

有两条关键决策：

  1. 先 docker stop trtllm_serve_step11 释放 7.4 GiB VRAM。nsys profile trtllm-bench latency 是独立子进程，要自己装载引擎（约 3 GiB 权重 + KV cache 池），8 GiB 卡塞不下两份。
  2. container 要加 --cap-add=SYS_ADMIN --security-opt seccomp=unconfined。nsys --trace=cuda,nvtx,osrt --sample=cpu 需要 perf_event_open 系统调用，普通容器默认 seccomp 会拦掉。
nsys profile \
  --trace=cuda,nvtx,osrt \
  --sample=cpu \
  --force-overwrite=true \
  --output profiles/stage1/nsys/qwen25_15b_512_128_latency \
  trtllm-bench --model "$HF_MODEL" --workspace "$WORKSPACE_DIR" \
    latency --backend tensorrt \
    --dataset data/synthetic_512_128.jsonl \
    --engine_dir "$ENGINE_512_128" \
    --concurrency 1 --num_requests 20 --warmup 5 \
    --report_json results/stage1/benchmark_raw/trtllm_bench_512_128_latency_nsys.json

flag采集内容能回答什么问题

核心发现：kernel time 拆解

从 cuda_gpu_kern_sum，按 kernel 总时间归类：

类别时间占比代表 kernel
GEMM（矩阵乘） ~61.5% 各种 sm80_xmma_gemm_bf16bf16_* 的 tile-size 变体
Sampling head ~31.2% batchApplyPenalty 14.2%, addBiasSoftMax 12.7%, topKStage1 3.8%, topKStage2Sampling 0.5%
Activation / Norm 融合 ~3.5% SiluMul, RMSNorm 的 fused kernel
Attention ~3.0% FlashAttn v2 prefill 1.9% + masked-MHA decode 1.1%
KV cache update + RoPE ~0.4% applyBiasRopeUpdateKVCacheV2

三个反常识的观察

观察 1 — Attention 只占 3%： 这和"LLM 推理 attention 主导"的常见印象不符。原因：
• 模型只有 1.5 B 参数，每层很小，attention 工作量小
• 使用了 GQA，num_kv_heads=2 而不是 num_attention_heads=12——KV cache 缩小 6 倍，attention 计算量也缩小
• max_seq_len=640，attention 时间复杂度 O(N²) 但 N=640 时绝对值很小
这意味着 flash attention v3、xformers 这些优化在这个 model size + sequence length 下带不来多少收益。对你这个 setup，attention 不是瓶颈。
观察 2 — Sampling 占 31%（比 attention 大 10 倍）： decode 头的代价被严重低估了：
• addBiasSoftMax 12.7% 是对 151 936 维 vocab 做 softmax。Qwen2.5 词表巨大，每个 token 都要走一遍这个 151k 宽的 softmax
• batchApplyPenalty 14.2% 是 repetition penalty，要遍历整个 vocab 给重复出现过的 token 减权重
• topKStage1/2 4.3% 是 top-K 采样的两阶段实现
对小模型来说，LM head 本身（hidden×vocab = 1536×151936 ≈ 234 M 参数）就比一个 transformer block 的参数还多。这是 sampling 看似过大的根本原因。
观察 3 — 一个 GEMM 就占 24.3%： 最大单一 kernel 是 sm80_xmma_gemm_bf16bf16_bf16f32_f32_nn_n_tilesize256x128x32_stage3_warpsize4x2x1_tensor16x8x16，700 instances × 874 μs。
这是整个 trace 里最值得用 ncu 深挖的单个 kernel。step 16 第一目标。
从 tile 名解读：256×128×32 的 BF16 输入，BF16 输出，n×n 主序。tile 256×128 这种偏宽的 shape 通常对应 MLP up/gate projection（hidden 1536 → intermediate 8960），M 维度大但 N 维度中等。

CUDA API 视角：CPU 全在等 GPU

APITime %callsavg ns注
cudaEventSynchronize91.2%320010 042 800主线程等 GPU 完成下一 token decode
cudaMemcpyAsync3.9%57 72724 084含 engine load 那一次 3 GiB H2D
cudaGraphLaunch_v100001.3%3 125143 864每 decode iter 一次 graph launch
cudaLaunchKernel0.7%23 57610 381其余 kernel 启动
关键数字：cudaEventSynchronize 3200 次。 3200 = 25 requests × 128 tokens。每生成一个 token，CPU 就 sync 一次等 GPU。这是单用户 decode 的根本同步模式：
生成第 N+1 个 token 依赖第 N 个 token 的 argmax，所以 CPU 必须等 GPU 把第 N 个 sample 写回来才能 launch 第 N+1 个 forward。没有 CPU/GPU overlap 的空间。
推论：花精力优化 Python 侧、scheduler、HTTP 路由都不会降低单用户 TPOT，唯一杠杆是让 GPU 那一段更快（量化、faster attention、更快的 sampling）。

引擎加载 + 卸载占了 NVTX 总时间的 ~60%（约 30 秒墙钟时间 vs 整段 bench 28 秒）。step 16 ncu 要跳过这一段，否则它会用昂贵的 kernel replay 重放 engine 加载这种一次性、不感兴趣的过程。具体做法：--launch-skip 200 跳过头 200 个 kernel launch。

step 16 预告

step 16 用 Nsight Compute (ncu) 对选定 kernel做硬件计数器层面的深挖。两个候选：

  1. sm80_xmma_gemm…tile256x128x32（24.3% 时间）—— 看它是 compute-bound 还是 memory-bound、是否打满 Tensor Core、占了多少 register/shared mem
  2. addBiasSoftMax（12.7% 时间，151k 宽 softmax）—— 看 memory access pattern 是 coalesced 还是 strided

ncu 比 nsys 慢得多（每个 kernel 会被 replay 多次以收集所有 counter）。要用 --launch-skip / --launch-count 精准锁定才不会跑一整夜。
