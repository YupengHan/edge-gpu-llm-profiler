Stage 1 · Step 11 — 启动 trtllm-serve 并验证 OpenAI 兼容端点

执行环境：RTX 3070 Laptop（8 GiB, sm_86）/ Ubuntu 22.04 / 驱动 575.57.08 / CUDA 12.9 host。 后端：TensorRT-LLM 1.0.0，引擎 trtllm_workspace/Qwen/Qwen2.5-1.5B-Instruct/tp_1_pp_1（step 9 编出来的 512/128 main 引擎，bf16）。 日期：2026-05-11。

为什么要切到 trtllm-serve（而不是继续用 trtllm-bench）

Step 10 的 trtllm-bench latency / throughput 已经给了 baseline 数字，但它有两个内在限制，所以接下来必须切到 HTTP serve 模式：

  1. 采不到流式 ITL（Inter-Token Latency）。 trtllm-bench latency 报的是 每次请求 的 TTFT 平均值和 TPOT 平均值，但拿不到"这次请求里第 17 → 第 18 个 token 之间隔了多少 ms"这种 per-token 时序。真实聊天体验的卡顿感（"突然停顿一下又冒一句"）只能从 ITL 时序里看出来。
  2. 没有 OpenAI 兼容的客户端层。 我们希望复用 OpenAI 协议的 streaming chat completions（data: {...} SSE）写客户端，这样 step 12 的脚本就能未来对照 vLLM / Ollama / SGLang 这些后端而不用改协议。trtllm-bench 是离线一次性走完的二进制 path，不暴露 HTTP。

所以 step 11 的目标只有一个：把 step 9 编出来的 .engine 装进一个 OpenAI 协议的 HTTP server，验证 /health、/v1/models、/v1/chat/completions（含 stream）都能正常响应。step 12 才真正去采 TTFT/ITL。

整体动作（三件事）

11a用一次性容器跑 trtllm-serve serve --help，验证 1.0.0 的真实 CLI（runbook 没在 1.0.0 上验证过）
11b用 docker run -d 起一个 detached 容器，挂 step 9 的引擎，server 在 0.0.0.0:8000 监听
11c从宿主机 curl 打三个端点 + 一次 streaming，确认协议格式与 step 12 客户端兼容

Step 11a — 探 trtllm-serve serve --help

第一次跑漏了 --gpus all，立刻 import 报错：

ImportError: libcuda.so.1: cannot open shared object file: No such file or directory
学习要点： 即使是只想看 --help，tensorrt_llm Python 包在 import 阶段就会去 dlopen libcuda.so.1（CUDA 驱动库）。这个 .so 是被 NVIDIA Container Toolkit 通过 --gpus 注入到容器里的，没有这个 flag 容器里就没有这个文件，即使你完全不会真的调 GPU。
规则：跑任何带 TRT-LLM import 的命令，必须 --gpus all。

加上后，trtllm-serve serve --help 顺利输出。和 runbook 对照，只有 一个 flag 漂移：

Runbook 写法1.0.0 实际接受处理
--backend tensorrt --backend [pytorch|trt] 必须用 --backend trt，tensorrt 会被 click 拒掉

其它 flag 完全对得上：--host, --port, --tokenizer, --max_batch_size, --max_num_tokens, --max_seq_len, --tp_size, --pp_size, --log_level。位置参数 MODEL 也确认接受 TensorRT engine 目录路径，不需要传 HF repo 名。

展开看 11a 完整命令 
docker run --rm --gpus all \
  --memory 4g --memory-swap 5g --shm-size 1g \
  --ulimit memlock=-1 --ulimit stack=67108864 \
  -v "$PWD":/workspace/rtx3070-trtllm-latency-lab \
  -w /workspace/rtx3070-trtllm-latency-lab \
  nvcr.io/nvidia/tensorrt-llm/release:1.0.0 \
  trtllm-serve serve --help \
  2>&1 | tee logs/stage1/trtllm_serve_serve_help.txt

这是 一次性 容器（--rm，前台跑完即销毁），不会和后面的 detached server 容器抢端口。

Step 11b — 起 detached server 容器

把启动逻辑写到 scripts/_step11_serve.sh 里，关键是最后一行用 exec：

exec trtllm-serve serve \
  --host 0.0.0.0 --port 8000 \
  --backend trt \
  --tokenizer Qwen/Qwen2.5-1.5B-Instruct \
  --max_batch_size 1 --max_num_tokens 640 --max_seq_len 640 \
  --tp_size 1 --pp_size 1 --log_level info \
  trtllm_workspace/Qwen/Qwen2.5-1.5B-Instruct/tp_1_pp_1
为什么用 exec： exec 让 trtllm-serve 进程取代外层 bash，成为容器里的 PID 1。这样 docker stop 发出的 SIGTERM 直接打到 trtllm-serve 上，uvicorn 能干净地关闭；如果不用 exec，bash 是 PID 1，bash 收到 SIGTERM 不会自动转发给子进程，docker stop 就会卡满 10s 默认 grace period 后被 SIGKILL，留下半死的端口占用。

宿主机这边的 docker run -d：

docker run -d \
  --name trtllm_serve_step11 \
  --gpus all \
  --memory 10g --memory-swap 12g \
  --shm-size 2g \
  --ulimit memlock=-1 --ulimit stack=67108864 \
  -p 8000:8000 \
  -v "$PWD":/workspace/rtx3070-trtllm-latency-lab \
  -w /workspace/rtx3070-trtllm-latency-lab \
  nvcr.io/nvidia/tensorrt-llm/release:1.0.0 \
  bash scripts/_step11_serve.sh
flag作用
-ddetached，后台运行
--name trtllm_serve_step11给容器固定名字，后面 docker logs / docker stop 都靠它
-p 8000:8000把容器内 8000 端口映射到 host 8000；host 这边的 curl localhost:8000 就能打进去
--memory 10g --memory-swap 12g不编译，只装载引擎和跑推理，10g 完全够（构建期间才需要 12g）
--shm-size 2gTRT-LLM IPC 需要更大的 /dev/shm，默认 64m 不够

启动后做一个轮询（每 5s 打一次 curl /health），第 4 次（约 15 秒）就返回 200。容器进入 Up 状态。这比 trtllm-bench build 那种从头编译快得多——因为 server 只是把磁盘上已经编好的 rank0.engine 反序列化进显存，不需要重新走 TRT graph build。

Step 11c — 端点验证 & 关键 API 漂移

(1) /health

返回 HTTP 200，body 为空。轮询已确认。空 body 是正常的——liveness 探针通常只看状态码。

(2) /v1/models

{"object":"list","data":[
  {"id":"tp_1_pp_1","object":"model","created":1778563339,"owned_by":"tensorrt_llm"}
]}
关键 API 漂移： 服务端报的 model id 是 tp_1_pp_1（引擎目录的最后一级名字），不是 Qwen/Qwen2.5-1.5B-Instruct。 step 12 的 streaming 客户端必须发送 "model": "tp_1_pp_1"，否则会被 404 "unknown model" 顶回来。 这一点 runbook 没提，是 trtllm-serve 1.0.0 的实际行为：当 MODEL 位置参数是个路径时，它用 basename(path) 作为 model id。

(3) /v1/chat/completions（non-stream）

请求：

curl -s http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "tp_1_pp_1",
    "messages": [{"role": "user", "content": "Say hello in one sentence."}],
    "max_tokens": 16,
    "temperature": 0
  }'

响应（摘）：

{"choices":[{"message":{"role":"assistant","content":"Hello! How can I assist you today?"},
             "finish_reason":"stop"}],
 "usage":{"prompt_tokens":35,"completion_tokens":9,"total_tokens":44}}
  • 模型按 chat template 渲染了 prompt（35 prompt tokens 远大于 user content 的 9 个 token），说明 server 自动套用了 Qwen2.5 的 chat_template.jinja
  • finish_reason=stop，自然 EOS 终止，没撞到 max_tokens=16
  • usage 字段齐全（prompt/completion/total token 数）

(4) /v1/chat/completions（stream=true）

SSE 协议每个 chunk 一行 data: {...}，关键字段是 choices[0].delta.content：

data: {"choices":[{"delta":{"role":"assistant"}}]}
data: {"choices":[{"delta":{"content":"Sure"}}]}
data: {"choices":[{"delta":{"content":","}}]}
data: {"choices":[{"delta":{"content":" here"}}]}
...
data: [DONE]

和 OpenAI 官方 streaming 协议完全一致——scripts/benchmark_streaming_openai.py 里的解析逻辑（line.startswith("data: ")，遇到 [DONE] 退出，delta.content 计入 piece 列表）无需修改就能直接用。

注意： streaming chunk 里的 delta.content 是 文本片段（detokenized text piece），不是严格意义上的"一个 token"。一个 token 可能被 server 拆成多个 chunk 输出（罕见，多见于多字节字符），多个 token 也可能合并成一个 chunk。所以 step 12 算出来的"per-piece ITL"≈ "per-token ITL"，但不是恒等。
对单用户聊天体验来说，这个 piece-level ITL 才是用户真正感知的卡顿粒度，反而比严格 token 级更有意义。

显存观察 — 8 GiB 卡的"刚刚好"

时间点memory.used / free (MiB)注释
server 起来前176 / 7665桌面+host 进程
跑完一次非流式 chat 后7437 / 404引擎 + KV cache 全部驻留

稳态 ≈ 7.4 GiB，剩 ~400 MiB headroom。粗略分解：

  • 权重：1.5B × bf16 = 1.5e9 × 2B ≈ 3.0 GiB
  • KV cache（max_seq_len=640，max_batch=1）：
    2 × num_kv_heads(2) × head_dim(128) × num_layers(28) × seq(640) × bf16(2B) ≈ 36 MiB
    实际占得多得多，因为 paged KV cache 默认 kv_cache_free_gpu_memory_fraction ≈ 0.9，TRT-LLM 把"剩余显存的 90%"全切成 page 池子（即使单 batch 没那么多 page 在用）。这是为吞吐预留的——单用户场景下浪费但不致命。
  • activation buffers / cuBLAS workspace / TRT plugin scratch：几百 MB
隐患： 只剩 ~400 MiB headroom 意味着 step 11/12 跑的时候不能让任何其他 CUDA 进程吃显存——包括 Chromium 的 NVENC、其他 docker 容器、桌面合成器的 OpenGL 后端。一旦 server OOM，bench 会半路 5xx，整轮数据作废。

step 12 预告 & 此刻需要记住的事

  1. 客户端 --model 参数必须是 tp_1_pp_1（不是 Qwen/Qwen2.5-1.5B-Instruct）。这是本步最大的 API drift。
  2. server 容器留着不要 stop。step 12 跑完后再 docker stop trtllm_serve_step11 && docker rm trtllm_serve_step11 收尾。
  3. step 12 跑 streaming bench 时，不要同时开 Chromium / 其他 CUDA 任务，避免吃掉那 400 MiB headroom 让 server OOM。
  4. step 12 期望的输出：results/stage1/benchmark_raw/streaming_512_128.jsonl，每行一条请求记录（TTFT/ITL p50/p90/p95/mean、E2E、output_pieces）。
