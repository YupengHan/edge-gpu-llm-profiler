本步要解决的事

step 12 跑出 55 行 jsonl，里面同时混着 cold 请求（每次 prompt 都不一样）和 warm 请求（prompt 轮转回开头，命中 prefix cache）。step 18 的 baseline summary 需要一个稳定可重跑的脚本能：

  2. 分别报 TTFT/ITL/E2E 的分位数
  3. 额外吐出一份 JSON 供 README / report 直接引用，免得未来手抄

runbook 里 step 13 原本就是"实现 scripts/summarize_streaming_jsonl.py"。这个脚本在 step 12 之前其实已经存在（把所有非 warmup 行混在一起算平均），但不会自动识别 cold/warm，所以 step 12 的笔记是我手工拆出来报的——这次把它做进脚本。

关键设计：怎么定义"warm"？

我们用一个简单但精确的判据：

对每行的 prompt_index 做"是否首次出现"判定。第一次见这个 prompt → cold；之前已经见过 → warm。

这背后的物理意义：TRT-LLM 的 prefix cache 只在prompt 前缀重合时才命中。如果某条请求的 prompt_index 在当前文件里之前从未出现过，server 这边对它的 KV cache 一定是空的——这就是 cold prefill。反过来同 prompt_index 第二次出现，server 几乎肯定能从 page table 里找到上一次的 KV 页，prefill 就跳过 → warm。

一个容易踩到的小坑：要不要把 warmup 行算进 "seen"？

我第一版脚本是这么写的：

seen = set()
cold, warm = [], []
for r in non_warmup_rows:
    pi = r['prompt_index']
    if pi in seen:
        warm.append(r)
    else:
        seen.add(pi); cold.append(r)

跑出来 warm 是 0 条。但 step 12 数据明明有 5 条 cache-hit 行。哪里错了？

Bug： 我把 warmup 行（request_index 0-4）整段 filter 掉再做判定，但 server 这边的 KV cache 是从 warmup 那一刻就开始积累的。warmup 用过了 prompt 0-4，等 measured 阶段轮转回 prompt 0-4（request 50-54）时，server 这边其实早就缓存好了——所以这些 measured 行应该是 warm。我的脚本看不见 warmup，于是把它们错认成 cold（"在我的 seen 里第一次见"）。

修复：读文件时单独记 warmup 行的 prompt_index，作为 prior_prompt_indices 传给拆分函数，把这些 prompt 预先放进 seen。

# 在主循环里
warmup_prompt_indices = []
for r in all_rows:
    if r['warmup']:
        warmup_prompt_indices.append(r['prompt_index'])
        continue
    measured_rows.append(r)

cold, warm = split_cold_warm(measured_rows,
                             prior_prompt_indices=warmup_prompt_indices)
学习要点： 这是一个非常典型的"system state 不等于 visible data"陷阱。脚本看到的 jsonl 里 warmup 行是"应该被忽略"的；但server 的 KV cache 状态是 warmup 已经污染过的。基准测试经常这样——客户端的视角和服务端的视角对什么算"开始"有不同定义。
类似的坑：你以为 warmup 是为了让 JIT 稳定 / TF32 cache 暖好；实际上有时它也会把 cache 暖到对后续真实请求"超额有利"，让 measured 区间看起来比真实生产更快。

顺手加的两个能力

1. flattened per-token ITL（向前兼容）

原脚本只看 itl_ms_mean / itl_ms_p95 这种"per-request" 统计——也就是每个请求自己内部的 ITL 平均/分位。这有个理论缺陷：

问法per-request p95flattened p95
"全部 token 里有多少占比卡 ≥ X 毫秒"不能准确回答能准确回答
"哪一个请求最慢"能不能
面向 SLO（服务等级目标）的 ITL P95是它的近似就是它

step 12 数据 ITL 分布非常窄（per-request p50=10.60, p95=10.76，跨度 1.5%），所以 per-request p95 已经足够接近真值。但为了让 stage 1 之后做 vLLM/llama.cpp 对比、做 nsys 关联时能拿到精确的 token-level 时序，我让 benchmark_streaming_openai.py 在每行 jsonl 里多写一个数组字段：

"itl_ms": [10.55, 10.61, 10.58, ..., 10.72]   // 127 个 gap

summarizer 看到这个字段时就把所有请求的 gap 数组拼起来算全局分位。当前 step 12 数据没有这个字段，summarizer 优雅地报"not in data (rerun with updated bench client to capture raw gaps)"——没有重跑 step 12，因为分布太窄收益不抵成本。step 17 stretch run 时新数据就会带上。

2. --json <path> 机器可读输出

避免 step 18/19 写 README 时手抄数字。生成的 results/stage1/streaming_512_128_summary.json 长这样：

{
  "source": "results/stage1/benchmark_raw/streaming_512_128.jsonl",
  "measured_requests": 50,
  "cold": { "ttft_ms": { "n": 45, "mean": 54.28, "p50": ..., ... }, ... },
  "warm": { "ttft_ms": { "n": 5, "mean": 15.91, ... }, ... }
}
